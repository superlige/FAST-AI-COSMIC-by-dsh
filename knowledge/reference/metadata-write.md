# 共享元数据写入总则

**每一项写入，用户确认一次。** 写元数据只有一条路：在写调用里附 `report`，工具在这一次调用里预演、按预演排出确认单弹给用户、用户确认后落库并回读。造数据、改数据不走这套（连的是纯测试环境），见文末两节。

1. **写调用。** 写探针（FormLayoutWriteProbe / FormRegisterProbe / FormRuleProbe 写模式 / BizRuleProbe 写模式 / BotpRuleSyncProbe / PrintTplWriteProbe）带 `APPLY=1`，或 `cosmic_meta` 的写动作带 `apply=true`，同时附 `report`。`cosmic_meta ptpl apply` 和直接调 `PrintTplWriteProbe` 是同一个操作。
   想先看会改成什么样：不带 `APPLY` / `apply` 跑一次就是预演，什么都不写。
2. **`report` 只填人话，其余由工具生成：**
   - `purpose`：这一项为什么做，一句话，≤40 字；
   - `names`：预演报出的每个标识的中文名（只写名字，一个不多一个不少；探针已经报了名字的不用填）；
   - `slots`：人话格，例如界面规则每组条件的人话说法（≤60 字）；
   - `note`：可选，一句注意事项（≤40 字）；
   - `decisions`：需求没说、由你选了做法的地方，每条 `chose` 一句做法、`other` 一句另一种（各 ≤60 字，不写标识），例如「下拉用字母存储值；另一种：用数字」。确认单上列在表单之后，用户确认改动时一并定。

   不知道要填哪些名字和格子：先不带 `report` 发写调用，工具预演后拒掉，并给出照着填的模板（只替换尖括号里的内容），这次什么都没写。
   人话格里不许夹标识（`demo_xxx` 这种），标识由工具显示在旁边一列。**确认单的其余部分全由工具按类别生成**：表头（单据 / 布局 / 模板，中文名和标识分两列）、表格（字段名称 | 标识 | 类型，规则 | 什么时候 | 管的字段 | 条件原文，编号 | 字段 | 原值 | 新值……）、影响、撤回、写入范围。
3. **用户确认后落库并回读。** 回来的结构化记录里，逐项改动折成条数，回读对不上的那几处原样列出。用户不确认就什么都不写，返回里带着用户说的话；按用户的意思改了再发写调用，会重新预演、重新确认。
   弹不了确认的地方（无头运行），写调用被拒、什么都不写，返回里附上确认单原文，交给用户在桌面版或网页版里做。

打印模板和 BOTP 规则同步落库时要给备份目录（`TPL_BACKUP` / `SYNC_BACKUP`，`cosmic_meta` 加 `--backup`）：它只决定改前快照存哪，忘了给会在预演之前被拒。

**写成没写成以探针自己的落库成功行为准，不看退出码。** 基线已变、平台校验不过、`save -> {success=false}` 这些中止都是退出码 0，一律按没写成算。

**写入范围不用抄。** 写探针在预演结束前会把这次会碰到的全部目标打成一行「写入目标清单」（布局、每个字段、`tpl:` / `botp:` / `wf:` 前缀），工具拿它当确认单上的写入范围，模型不经手。落库时只能写这个范围里的对象（IsvGuard 在 JVM 里逐个比对）。**落库时被门禁拦下不等于写坏了**：那一刻共享环境一个字节都没动，返回会写「没有落库」而不是「写入失败」，不用去核对现场；重新发写调用就按现状重新预演、重新确认。

**写入失败不要重试**：写失败可能已经部分落库，接着写就是对未知现场盲写，先用只读探针看现状（在写入之前被门禁拦下的那种除外）。同一张单据上的改动写进一个调用（`FormLayoutWriteProbe` 的 `LAYOUT_EDIT`：加字段、调位置、改属性、加按钮一次预演、一次确认、一次落库）。

**纯元数据改动不需要编译。** 本会话改过的业务 `.java` 没编译新鲜时，写调用在预演前被拒；工程里别人没编译的 Java 不拦（写探针不加载业务类）。能用 `cosmic_run --expect` 断言的就照常断言一次；没有可跑的验证（界面显隐、打印效果、转换结果这类），完成情况里写清要用户打开哪里、看什么，不要编一条断言。默认在常驻进程写入并回读确认；显式冷进程写入后，常驻进程重启再读取。

## 造测试数据（DataSeedProbe）

有些逻辑要先有真数据才验得了：列表、报表、后台任务、别的进程读数、用户自己打开界面看效果。**临时探针不能写数据**（写了会被拒），写入口只有两个已发布探针：新建用 `DataSeedProbe`，改已有数据用 `DataUpdateProbe`（见下一节）。

**直接落库，不用确认**（连的是纯测试环境，业务数据坏了能从生产复原；只有写元数据要确认）：参数写好就落库（不用加 `APPLY`），不弹确认，走常驻 JVM，十几秒。**不限 ISV**：原厂单据也能造、能改。

- **入参**：`SEED_ENTITY`（单据或基础资料）；`SEED_OPS` 操作链，逗号分隔、按顺序执行，默认 `save`，例如 `save,submit,audit`；造一条用 `SEED_SET`（写法同 `cosmic_run op` 的 `--set`），造多条用 `SEED_ROWS`（每条以 `[row] 标签` 起头，下面跟 `set=…`，可选 `ops=…` 覆盖 `SEED_OPS`、`copy=…` 换一张照着复制的）。
- **三种起点**，按要的数据选：

  | 要的数据 | 写法 | 自己要给的字段 |
  |---|---|---|
  | 和现成某张差不多，只改几个字段 | `SEED_COPY=单据编号或 pk` | 只写这次要不同的（`SEED_SET`） |
  | 要挂在上游单下面（验反写、关联查询、上查下查） | `SEED_FROM=源单标识:编号`；源单到本单有多条启用规则时，按这几张源单挑满足源单条件、推得出来的那条（用了哪条会说），要指定写 `SEED_RULE`；只写源单标识就按规则的源单条件挑一张推得出来的，这时多条规则要写 `SEED_RULE` | 下推带不过来、又要改的 |
  | 环境里没有这类单可照 | 只给 `SEED_SET` | 必填和取值全部自己给 |

  上游也要先造时，先 `SEED_COPY` 一张上游、`SEED_SET` 改上源单条件里的字段、`SEED_OPS` 走到条件要的状态（常见是 `save,submit,audit`），再拿它的编号 `SEED_FROM` 下推。
- **预演可选**：加 `PREVIEW=1` 在回滚事务里把整条操作链跑一遍、不落库，固定走冷进程（约 40～90 秒）。落库按平台自己的事务逐条提交（和界面上保存一样），存不进去照样当场报出来，没跑通时前面已提交的几条留在库里、逐条列出。
- **边界写死、没有开关**：只新建，不改、不删已有数据；走单据自己的操作链，校验器和插件照常跑；一次最多 50 条；任何一条、任何一步不成功就停，已提交的留在库里、逐条列出。
- **链上插件发消息、调接口照跑**：单据的插件链上登记了这类动作时，结果里提醒一句「会真的发出去」，不拦。
- **数据留在环境里，不自动清理**：落库后探针按 pk 回读，全部找到才算写成；造出来的编号和 pk 列在执行结果里，`cosmic_facts` 也列出本会话造过的每一条。
- **要编译到最新**：造数会加载业务插件，工程里有没编译的源码会被拦，先 `cosmic_fast`。
- **它不算要交代的改动**：只造了数据的会话，照样要有能跑的验证；**在它之前跑出来的断言运行不算数**——先造数，再跑验证。

### 平台的复制和下推各带过来什么

**复制**（界面上的「复制」按钮，`SEED_COPY` 走的就是它）：

- 字段的「是否复制」勾着的带原值；没勾的和系统字段（单据编号、单据状态、创建人、创建时间、审核人这类）填默认值：单据状态回到暂存，单据编号保存时按编码规则重新给号。
  没勾的不只系统字段，业务字段也有，常见的是界面上某个按钮、某一步流程才补上的值；它们复制出来是空的。
  `SEED_COPY` 会列出「原单有值、复制出来空着的字段」，后面下推、提交要用到的，用 `SEED_SET` 补上。
- 分录整行带过来、行重新生成；多选基础资料重建一份带过来。
- **下推关联不带**：复制出来的单没有上游，在上查、下查、反写里都看不到它。要验这些，这张单得从上游推出来。
- 表单插件的复制后事件照常触发：插件在复制时清掉、改掉的字段，以复制出来的结果为准。
- 第一步操作（通常是保存）在复制出来的表单上点，和界面上一样先过表单插件的操作前事件：编码规则在这一步给号；
  表单插件在操作前取消时，返回里列出它弹给用户的话。

**下推**（界面上的「下推」，`SEED_FROM` 走的就是它）：

- 一对源单、目标单常有好几条转换规则（比如按业务类型分开），每条有自己的「源单数据筛选」条件；不满足条件的源单推不出来，平台只回一句「不符合转换规则的数据筛选条件」。
- 满足条件还推不出来，常是转换插件读了源单上某个空着的字段，平台只回插件抛的那句话，看不出读的是哪个字段。
  `SEED_FROM` 推不出来时（写了编号推不出来的，或只写标识时挑单被跳过的）逐张说平台的原因，再拿满足同样条件、已经推出过本单的几张源单比，
  列出它们都有值、这张空着的字段；比出来没有，就是规则或插件本身的问题，换规则。
- 推出来的单带下推关系；目标单保存、审核时，规则上配的反写照常回写上游。

## 改数据（DataUpdateProbe）

验逻辑常常要把现有数据改成某个状态：结论改成不合格、数量改成 0、日期改到上个月。先用 `DataQueryProbe` 查清要改哪几条，再用它改，同样直接落库，不用确认。
只为跑一次 `run op` 时让上游（或下游）单是某个样子，不用它：`run op` 的 `--set @上游.<单据标识>.<字段>=值` 跑之前改上、跑完改回，见 [run.md](run.md#run-op操作插件)。
**每条每个字段的原值和新值由探针从库里读出来**，进执行结果，不经模型转述：

```
【1】修改数据（数据）  D1
  单据      检验委托单  demo_qty_wtd
  保存方式  保存（校验器和插件照跑）
  条数      2 条
  目的      测试环境直接落库（写数据不用确认）

  编号      字段      原值  新值
  WTD-0001  检验结论  空    不合格
  WTD-0002  检验结论  合格  不合格

  影响  走单据的保存，校验器和插件照跑；别人看到的数据立即变
  撤回  按上表的原值再改回去（改数结果里保留原值）
```

- **选中要改的数据**（三选一，或者用 `UPD_ROWS`）：`UPD_PKS=pk1,pk2`；`UPD_NUMBERS=编号1,编号2`（单据编号，基础资料是编码）；`UPD_WHERE=条件`，写法和 `DataQueryProbe` 的 `QUERY_WHERE` 一样（`;` 是并且、`|` 是或者），命中超过 50 条整批不跑。
- **改成什么**：`UPD_SET=字段=值;字段=值`，选中的每条都改成这组值，写法同 `--set`（分录写 `分录[0].字段`，基础资料给 id 或编码，写 `null` 清空）。每条改成不同的值用 `UPD_ROWS`：`[row] 编号或pk` 起一条，下面跟 `set=…`。
- **怎么存**：`UPD_OP` 默认 `save`，校验器和插件照跑；已审核的单据平台不让保存，确实要改就写 `UPD_OP=direct` 直接存库，不走校验器和插件。
- **存完就回读**：事务里设值、保存、按 pk 回读，要改的字段有一个不是新值（多半是保存时插件又改了它）就整批回滚、算没改成；字段写错、值转不过去、编号对不上，一次列全后失败，一条都不改。预演（`PREVIEW=1`）可选，冷进程。
- **链上插件发消息、调接口照跑**：结果里提醒一句；不想触发就 `UPD_OP=direct`。
- **不会自动改回**：落库后每一格「编号 字段：原值 → 新值」进执行结果，`cosmic_facts` 也列出本会话改过的每一格，要恢复就照原值再改一次。
