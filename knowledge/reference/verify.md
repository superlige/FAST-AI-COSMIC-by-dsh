# 验证与交付

**可自动验证的改动，交付要求本次会话、在当前这份代码上、最后一次共享写入之后有 `cosmic_run --expect` 断言全过的运行。**
纯元数据和内核判定无自动验证路线的改动可出待人工验收回执，具体条件见下文；纯元数据不用编译。`cosmic_verify action=finish` **不重跑任何运行**——它核对的是你刚才已经跑过的那些运行，几秒钟出结果。
本会话造过、改过数据的，交付前在已经在跑的常驻进程里按主键回读那几张单还在不在（只读，每类单约 1 秒），
回执照回读写「还在 / 已经查不到 / 没回读成」：之后删掉了的单不用再清理、不用再改回；改过的格子列的是本工具最后写入的值。回执不是需求记录；它没有编号、状态或跨会话检索。线上部署验收由用户完成。

**没改东西就没有交付。** 本次会话没改业务代码、没写元数据、没用造数改数探针写数据（探查环境、查数、跑验证、写文档这类活），
`preflight` 答 `NOTHING_TO_DELIVER`，`finish` 答「没有要交付的改动」、不出回执；做完直接把结果告诉用户。
临时探针（`.cosmic-ai/probes/` 下）不算改动；写过又删掉的业务文件、写失败的共享写入、造数改数探针造过改过的数据都算。
`cosmic_run` 真提交改过的单不算要交付的改动、不出回执，改了哪些单在回答里一并告诉用户。

断言运行不会存成回归用例：苍穹的元数据、共享数据、配置天天在变，今天存的期望值明天就可能不成立。
真要长期守住的回归，写进工程自己的测试里。

## 验证记录：每次断言运行留下的一份事实

每次带 `--expect` 的 `cosmic_run` 会在 `.cosmic-ai/evidence/assertions/` 留一条记录，写着：
在哪个环境（RuntimeKey）、哪份代码（源码指纹）、跑了什么命令、每条断言过没过、日志在哪，
外加一个内容摘要。会话状态里只记编号和摘要、**不记结论**——所以改记录文件想把失败变绿是没用的：
摘要对不上，那条记录直接不认。

判定时按**场景**归并：一条命令去掉 `--expect` / `--show` 之后剩下的部分就是场景键。
所以「期望值写错了，改对再跑一遍」算同一个场景的第二次，**以最后一次为准**。
换单据或修改输入参数会成为另一个场景，不能替换原失败。仍有失败时，finish 出 `PARTIAL` 部分完成回执：
通过和未通过的运行、失败断言的期望和实际值、原始命令和日志都保留；退出码为 1，不记为已交付。
这份回执用于如实交代进展，不表示全部验证通过，也不会把失败作废。已落库的操作复查先读日志，不为纠正断言而改状态、反审核或重复提交。

两个配套的行为：

- **输入写错不留记录。** 目标（模板编码、单据）、`--pk` 查不到，`--set` 的路径写错、基础资料对不上或下拉写成显示名，
  验「会被拦」时拦住它的不只是写明的原因（挑的单本来就过不去），
  探针报「✘ 输入不成立」，这次不留验证记录。这几样都在场景键里，改对之后是另一个场景；
  要是留成一条 FAIL，它就永远换不掉，交付被一个错字挡住。这次什么都没验，不留记录也放不过任何失败。
- **顶掉 PASS 时当场说。** 同一个场景先过、后来又跑了一次没过（比如拿同一组 `--pk` / `--set` 故意跑反例），
  那次运行的返回里就会写明「那次的 PASS 已经被顶掉」，不用等到 finish 才发现。

## 五条不会松的线

1. **业务 Java 必须编译到最新**：业务源码动过、没重新 `cosmic_fast`，finish 直接拒；纯元数据不用编译。
2. **断言必须真跑真过**：`EXECUTED`（跑通了但一条断言都没有）**不算验过**。
3. **共享写入之前的结果不算**：改元数据之前跑的全绿，改完之后**要重新跑一遍**。
   按每条记录的时间戳判。
4. **降档跑出来的结果不算**：关掉门禁跑出来的绿不作数。
5. **模型改不了证据**：每条验证记录带内容摘要，改了记录文件摘要就对不上，那条直接不认（见「验证记录：每次断言运行留下的一份事实」）。

转换插件交付必须有 `run push` 的保存后数据库回读记录，而且该规则启用的插件包含本次修改的转换插件。只验失败提示或仅有内存断言不算落库确认，预检会给出保存回读命令，finish 只能出 PARTIAL。

源码变化后，重新读取工具列出的文件及行段，查看 `git diff`，核对取数、复制及赋值，再编译验证。旧证据产生于改动之前；编译不等于已经理解变化，也不能让旧证据重新有效。

## PASS 说的是「跑过的那几条断了」，不是「这个需求验完了」

这两句话差一次线上事故：一次 `run form --click 某按钮` 五条断言全绿，而改动里有一半只在弹窗关闭的
`closedCallBack` 里执行，那一半执行次数是 0，回执照样 PASS。所以报完成之前逐条问一遍：
**我改的每个方法，有哪条断言真的走到了它？** 入口传 null 参数的分支、只在回调里被调的分支，一律不得算「已验」。

`run form` 跑完会打一段「本次入口走到了哪些回调」，把插件重写了、而这次一次都没触发的回调
列出来（`closedCallBack` / `click` / `confirmCallBack` …）。改动落在那几个名字里的话，
这次的绿证明不了它——换一个能走到它的入口再验，或者在交付里照实写「这段没验」。

**改的类该怎么验，不用自己想。** 编译通过、进入 verify 时自动跑的那次预检会按源码认出每个改动类是哪类插件，
查验证路线表，逐个给出样板命令，例如 `MetalPrint（打印插件）→ cosmic_run print <模板编码> --pk <单据ID> --expect <格子>=<值>`；
认不出类型的普通类给 `cosmic_run call <类名>#<方法> …`。尖括号换成实际值就能跑。

**动手之前先按「能不能驱动」把改动分组。** 有的分支根本没有已发布通道能驱动（典型是要人在
真界面上点一下的那类）。这种情况下唯一正确的动作是：验完其余部分，然后**停下来**说明
「这一组验不了、需人工验收」，而不是去找旁路。工具说「本通道驱动不了」时，那就是停下来的信号。

**临时探针自己打的 PASS 不算交付证据。** 探针是你自己写的，想断言什么都行；交付只认 `cosmic_run --expect`。
探针输出里有断言时，结果会带一句提醒。

## 修报错：先把报错原文跑出来，再改

用户报错时一句话里常有三样：报错原文、他判断的原因、他要的改法。原文和调用栈是环境说的，后两样要验。
改动对不对，看的是这句原文在改动之前跑得出来、改动之后同一条命令跑不出来。

**「跑出来」用不着出错的那条数据。** 报错多半来自别的环境，这里没有那张单是常事。要的是按认定的原因把条件造出来，
输出里出现同一句话：造一张满足条件的单跑操作，`cosmic_run call` 直接调出错的方法并传那个值，或者写一个只读探针。
单据号、内码、日期和原文不一样没关系，实体和字段标识要一样。

**两个候选原因各造一次条件**：跑出同一句的那个成立，跑出另一句话的那个不成立。例如报错里字段名的位置是空的，
`row.get("")` 跑出的就是这一句；读一个没加载的字段，跑出的是带着字段名的另一句。

**先跑出来再改，改完同一条命令再跑一遍。** 直接调平台接口把原文跑出来的探针走不到业务代码，它能证明原因，证明不了修好；
要证明修好，用一条走得到改动代码的命令（跑操作、开表单、`run call` 业务类的方法）在改动前后各跑一次。

**造不出条件时照实说。** 依赖出错环境才有的配置、外部系统、真浏览器的，交付时告诉用户两件事：原因是推断的、依据是什么；
到出错的环境里看哪条数据或哪行日志就能确认。

## 交用户验收：只有两种情况能走

两种情况下没有能跑的断言运行，finish 也不拒，而是出一张 `USER_ACCEPTANCE` 回执，明说「没有自动验证」：

1. **纯元数据交付**：本会话写成了共享元数据、没动任何业务 `.java`。回执列出授权时确认的每项修改
   （对象 / 改什么 / 原来 / 改后）、写入结果、回滚方式。
2. **改的类全都没有自动验证方法**：预检判为 `NO_AUTOMATABLE_PATH`（例如只改了报表界面插件、
   收 HTTP 请求的接口 servlet）。finish 时必须带 `acceptance` 写清三件事，缺一件就拒：
   `checked` 这次实际查过什么（编译通过、只读探针读到的配置）、`unchecked` 没验到什么、
   `userSteps` 用户要自己打开哪里、点什么、看到什么才算对。回执标「待人工验收（不是通过）」，三件事原样列出、注明是 AI 写的。

**「没有自动验证方法」由内核判，不能自己声明。** 改动里只要有一个类有路线（包括认不出类型的普通类，它总能 `run call`），
带 `acceptance` 来 finish 会被拒（`VERIFY_ACCEPTANCE_REFUSED`）。**混合改动不走这条路**：有路线的那一半照旧要有断言运行证明；
验过之后出的 PASS 回执会在边界里点名没路线的那几个类，要用户自己验。

## 三个动作

| 动作 | 干什么 |
|---|---|
| `finish`（默认） | 交付改动的唯一一条路：核对本次会话跑过的断言运行，出回执；全部通过才记为已交付，有失败出 PARTIAL，不重跑任何东西；出回执时把交付报告直接显示给用户（要带 `report`，见下文）。返回里只有回执正文（结论、每条命令、每项改动一行、边界）和回执文件路径，逐处明细和全文在文件里；要整份回执对象和验证记录原文带 `raw=true` |
| `preflight` | 不写状态，只把「现在交付还缺什么」一次说完。`fast` 编译新鲜时会自动跑一次，通常不用另外调 |
| `show` | 把本次会话验过哪几条、最近一张回执摊开给人看 |

`preflight` 给的是六条路之一，每条都带下一步该敲什么：

- `NOTHING_TO_DELIVER`：本次会话什么都没改，没有要交付的，不用 `finish`。
- `READY_TO_DELIVER`：有断言全过的运行，下一步 `finish`。
- `USER_ACCEPTANCE`：纯元数据改动，不用编译，下一步 `finish` 出交用户验收的回执。
- `NEEDS_EXPECTED_RUN`：还没有能当证据的运行，先用 `cosmic_run` 带 `--expect` 跑一次业务断言。
- `FAILING_SCENARIO`：有场景最后一次没过，finish 可出 PARTIAL 部分完成回执；失败保留，不记为已交付。
- `NO_AUTOMATABLE_PATH`：改的类**全部**属于没有自动验证方法的插件类型。不用再找验证办法：做完预检列出的只读检查，
  finish 时带 `acceptance` 三件事，出「待人工验收」回执。

**交付报告直接显示给用户，你写的那几句放在 `report` 里。** 出回执的 finish 必带 `report`：
`need` 需求一句话；`changed` 改了什么；`points` 需求里每一点一条——`done` 做到了什么（带一个具体例子，例如「12.500 打成 12.5」）、
`check` 怎么验的（例如「试了 4 种组合，该显示的列都对」）、`runs` 验它的那几次运行编号（`cosmic_run` 返回里的 `AE-…`，没有自动验证的留空）；
可选的 `runs`（每次运行验了什么，一句话）和 `userCheck`（要用户自己看、工具列不出来的，例如用哪张单预览）。
都用用户的说法：用户认得「拉伸试验原始记录（圆管）」，不认得模板编码。字段标识、类名、路径、命令写进去会被拒，
每句不超过 120 字，`runs` 只能点本次采信且通过的运行（点了被同一场景后一次顶掉的，后一次通过才替换）。失败由工具自动列出，不能在报告里当成验过。
结论、跑了几次核对几处、没验到的层（打印版面、没部署、没有自动入口的对象）、留在环境里的数据、替用户定的口径、写法提醒，
工具按事实补上，不用你写。报告用户已经看到了，回复里不再复述，只说报告里没有的，例如和本次无关的既有报错。
运行不回滚；回执照每次运行日志里的写库语句写明哪几次真写了库、写了哪些表，日志里没有写库语句的算没改数据。
没改 `.java` 时，回执分开写这次动过的是非 Java 文件、元数据还是测试数据。

**替用户定的口径进回执开头。** 确认单上列过的（`cosmic_authorize` 的 `decisions`），finish 自动带上，不用再写；
没上过确认单的——改 Java 时自己选的做法、确认之后才定的——finish 带 `decisions` 补上，每条 `chose` 一句做法、`other` 一句另一种，
例如「第一行的集合复制给其余行；另一种：每行各建一份新集合」。交付报告里每条一行，不合意用户当场能说。

**`show` 故意不做判定。** 它只摊事实：本次会话有哪几条记录、各自什么结果、日志在哪，外加最近一张回执。
能不能交付去问 `preflight`。两个地方各判一次，迟早出现「show 说有 3 条、finish 说一条都不算」这种没法查的输出。

## 回执里有什么

回执绑三样东西：环境身份（RuntimeKey）、源码指纹、**本次采信的那批验证记录的摘要**
。除此之外它列出：

- `verification.runs`：采信的每一次运行——记录编号、**完整命令**（照抄就能复查）、场景摘要、
  几条断言、结果、时间、日志路径，以及这次是付了冷启动还是搭的常驻 JVM；
- `files` / `anchors`：本次改了哪些文件、挂在哪些点上，取自会话自己的工作轨迹，不是模型重打的；
- `limitations`：「这次没验到什么」，**内核按事实生成，模型只能追加、不能替换**；
- `sharedWrites` / `changes`：本次写进共享环境的元数据修改；
- `acceptance`：只在「改的类没有自动验证方法」那种回执上有，就是 finish 时写的三件事。
- `decisions`：替用户定的口径，排在回执开头、改了什么之前。确认单上列过的由工具带进来；没上过确认单的标「交付时才说」。
- `story`：交付报告里你写的那几句，核对过的样子（`points` 的运行编号已换成采信的那一次）。

全绿也不等于线上验收通过。
