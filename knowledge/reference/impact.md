# 影响面索引

用 `cosmic_impact` 从线上元数据和本地 Java 源码查改动牵动什么；xml、js、配置、日志等别的文件不在扫描范围，用户点名了就自己读。

- **字段查询有三种写法**：单写 `字段` 查各张单上的同名读写；`单据实体.字段` 限定一张单；`单据实体.分录.字段` 再指定分录，子分录继续加层。这里的单据实体是整张单据的标识，不能用分录标识代替。
  例如 `demo_bill.demo_entry.demo_field`；`demo_entry.demo_field` 缺少所属单据。只知道分录和字段时，先单查 `demo_field`，确认所属单据后再限定。
  报错说首段未识别为单据实体、但字段已收录时，按返回的字段重查命令继续；该查询是跨单据的同名读写，不能把所有结果都当成原单据的。没有元数据快照时，字段归属和插件挂载可能无法确认，未收录不等于不存在。
- **限定到单据的字段查询**：返回这张单上读写这个字段的每一处，写成 `类#方法:行` 加写法（`set`、`getString`、按条件读、取数读……），按挂载插件分组，插件不在单据自己的布局上时写出挂在哪个布局。
  从插件被平台调用的方法起逐层写到读写处，几个事件方法都走到就各列一条，如 `XxxPlugin#query:32 → XxxUtils#dealRate:2285 写 set`，末尾给文件路径。
  归属看读写的对象从哪来（插件挂的单、按名字加载的单；参数传进来的到调用处接着认，行尾注明在哪一层认出）；
  对象是别的单或只能按名字猜的只报个数和原因，`dynamic=true` 逐处列出。找不到挂载插件、字段不在这张单或这条分录上的，都说明原因和实际位置。
  元数据快照只收每张单自己设计里的字段：从模板继承来的（`billno`、`billstatus` 这类，或本 ISV 模板上的字段）不在里面，这时只说「快照没记到」并写出这张单继承自哪；能断定「不在这张单上」的，才这样说。
- **查类名、布局标识、元数据对象编号**：每个类给挂在哪、写了哪张单的哪些本工程字段、同字段还有谁在写（按读写的对象认单，不按同名猜）、牵连的元数据对象。
- **查实体标识**：登记在这张单上的插件按表单布局、单据操作、打印模板等位置分组计数，另列按名字读写它的类、不止一个入口在写的字段。
  读了哪些单据、调用链、归属不明的字段，加 `dynamic=true` 逐条列。

**没列出不等于没用到**：表里记字段名是字面量、常量或常量数组（循环里逐个取）的读写、分录操作、查询条件、取数字段串、操作预加载、转换源字段，经包装方法传的记在调用那一行，
`分录.字段`、`基础资料.属性` 算它碰到的字段；放进 Map、界面控件、按名字比较的不记。
字段名或单据名在变量里、按序号取的，表认不出是哪个，回答里按类列出方法和行号（默认前 8 处，`dynamic=true` 列全），碰的是什么读那几行源码。行号对当前源码（查询前先重建）。
