# 验证与完成情况

**可自动验证的改动，要在本次会话、当前这份代码上、最后一次共享写入之后，有 `cosmic_run --expect` 断言全过的运行。**
只用 `--show` 看值的运行算「跑起来了」，不算验过。纯元数据改动不用编译。
做完之后调一次 `cosmic_facts`，照它列出的事实按系统提示里的模板写完成情况：它列现在和本会话开始时的净差别——
业务代码改前改后、写进测试环境的元数据（按对象，带确认单和撤销办法）、跑过的断言（过没过、之后改没改过代码）、留下的造数，每项都报数，0 也报。

**没改东西就没有要交代的改动。** 探查环境、查数、跑验证、写文档这类活，做完直接把结果告诉用户。
临时探针（`.cosmic-ai/probes/` 下）不算改动；`cosmic_run` 真提交改过的单留在测试环境，改了哪些单在回答里一并告诉用户。

断言运行不会存成回归用例：苍穹的元数据、共享数据、配置天天在变，今天存的期望值明天就可能不成立。
真要长期守住的回归，写进工程自己的测试里。

## 验证记录：每次断言运行留下的一份事实

每次带 `--expect` 的 `cosmic_run` 会在 `.cosmic-ai/evidence/assertions/` 留一条记录，写着：
在哪个环境（RuntimeKey）、哪份代码（源码指纹）、跑了什么命令、每条断言过没过、日志在哪。

写完成情况时按**场景**看：一条命令去掉 `--expect` / `--show` 之后剩下的部分就是场景。
「期望值写错了，改对再跑一遍」是同一个场景、同一种期望，**以最后一次为准**；
同一组 `--pk` / `--set` 先验一种结果、再验另一种（先放行再拦住，比如首次下推成功、重复下推被拒），期望不同，各自最后一次过了都算。
换单据或修改输入参数会成为另一个场景，不能替换原失败；仍有失败就照实写「没过」，失败的期望和实际值、命令、日志都留着。
已落库的操作复查先读日志，不为纠正断言而改状态、反审核或重复提交。

- **输入写错不留记录。** 目标（模板编码、单据）、`--pk` 查不到，`--set` 的路径写错、基础资料对不上或下拉写成显示名，
  验「会被拦」时拦住它的不只是写明的原因（挑的单本来就过不去），
  探针报「✘ 输入不成立」，这次不留验证记录。这几样都在场景键里，改对之后是另一个场景。

## 什么样的结果算验过

1. **业务 Java 编译到最新**：编译之后又改过的 Java，`cosmic_run` 在跑之前就拒；纯元数据不用编译。
2. **断言真跑真过**：跑通了但一条断言都没有，不算验过。
3. **共享写入之前的结果不算**：改元数据之前跑的全绿，改完之后要重新跑一遍。
4. **降档跑出来的结果不算**：关掉门禁跑出来的绿不作数。

转换插件要有 `run push` 的保存后数据库回读，而且该规则启用的插件包含本次修改的转换插件。只验失败提示或仅有内存断言不算落库确认。

源码变化后，重新读取工具列出的文件及行段，查看 `git diff`，核对取数、复制及赋值，再编译验证。旧结果产生于改动之前；编译不等于已经理解变化，也不能让旧结果重新有效。

## PASS 说的是「跑过的那几条断了」，不是「这个需求验完了」

这两句话差一次线上事故：一次 `run form --click 某按钮` 五条断言全绿，而改动里有一半只在弹窗关闭的
`closedCallBack` 里执行，那一半执行次数是 0，结果照样 PASS。所以报完成之前逐条问一遍：
**我改的每个方法，有哪条断言真的走到了它？** 入口传 null 参数的分支、只在回调里被调的分支，一律不得算「已验」。

`run form` 跑完会打一段「本次入口走到了哪些回调」，把插件重写了、而这次一次都没触发的回调
列出来（`closedCallBack` / `click` / `confirmCallBack` …）。改动落在那几个名字里的话，
这次的绿证明不了它——换一个能走到它的入口再验，或者在完成情况里照实写「这段没验」。

**改的类按插件类型挑入口：**

| 改的是 | 用 |
|---|---|
| 表单插件（按钮、值更新、加载） | `cosmic_run form`，点按钮带 `--op` / `--click` |
| 操作插件（保存、提交、审核的校验和服务） | `cosmic_run op` |
| 列表插件 | `cosmic_run list` |
| 父子页回调（`closedCallBack` 一类） | `cosmic_run callback` / `flow` |
| 界面规则（显隐、锁定、必录） | `cosmic_run rule` |
| 打印插件 | `cosmic_run print <模板编码> --pk <单据ID>` |
| 转换插件 | `cosmic_run push <规则id>`（目标单保存后从数据库回读） |
| 工作流插件 | `cosmic_run wf` |
| 其余本工程的普通类 | `cosmic_run call <类名>#<方法>` |

每个子命令的参数写法：`cosmic_run argv=["help","<子命令>"]`。

**动手之前先按「能不能驱动」把改动分组。** 有的分支根本没有已发布通道能驱动（典型是要人在
真界面上点一下的那类，或者报表界面插件、收 HTTP 请求的接口 servlet）。这种情况下唯一正确的动作是：验完其余部分，
然后**停下来**说明「这一组验不了、需人工验收」，并写清用户要打开哪里、点什么、看到什么才算对，而不是去找旁路。
工具说「本通道驱动不了」时，那就是停下来的信号。

**临时探针自己打的 PASS 不算验过。** 探针是你自己写的，想断言什么都行；验过只认 `cosmic_run --expect`。

## 修报错：先把报错原文跑出来，再改

用户报错时一句话里常有三样：报错原文、他判断的原因、他要的改法。原文和调用栈是环境说的，后两样要验。
改动对不对，看的是这句原文在改动之前跑得出来、改动之后同一条命令跑不出来。

**「跑出来」用不着出错的那条数据。** 报错多半来自别的环境，这里没有那张单是常事。要的是按认定的原因把条件造出来，
输出里出现同一句话：造一张满足条件的单跑操作，`cosmic_run call` 直接调出错的方法并传那个值，或者写一个只读探针。
单据号、内码、日期和原文不一样没关系，实体和字段标识要一样。

**两个候选原因各造一次条件**：跑出同一句的那个成立，跑出另一句话的那个不成立。例如报错里字段名的位置是空的，
`row.get("")` 跑出的就是这一句；读一个没加载的字段，跑出的是带着字段名的另一句。

**先跑出来再改，改完同一条命令再跑一遍。** 直接调平台接口把原文跑出来的探针走不到业务代码，它能证明原因，证明不了修好；
要证明修好，用一条走得到改动代码的命令（跑操作、开表单、`run call` 业务类的方法）在改动前后各跑一次。

**造不出条件时照实说。** 依赖出错环境才有的配置、外部系统、真浏览器的，完成情况里告诉用户两件事：原因是推断的、依据是什么；
到出错的环境里看哪条数据或哪行日志就能确认。

## 完成情况里每一块写什么

用户一次需求常说不全、要来回改；完成情况说的是最后的样子，不是这一路改了几回、编译跑了几次。

- **现在的逻辑**：照 `cosmic_facts` 的代码差别，用用户的说法（「拉伸试验原始记录（圆管）」，不是模板编码）逐条说业务规则：
  哪个单据、什么时候触发、什么条件、做什么，带一个具体例子（「12.500 打成 12.5」）。
  每条后面标验没验：「真跑验过」写是哪条 `cosmic_run`；`cosmic_facts` 标了「之后又改过代码」的那次不算。
  没验的写原因和用户怎么手工验，没验到的层（打印版面、没部署、没有自动入口的对象）也挂在对应那条后面。
- **改了哪些元数据**：按对象写改前→改后，取 `cosmic_facts` 里确认单上那张表；同一对象写过几次，同一项以最后一次为准。
- **还要用户定或做的**：替用户定的口径（写元数据时确认单上列过的，和改 Java 时自己选的做法：每条一句做法、一句另一种）、
  留在测试环境的造数改数、要用户自己验的步骤。

全绿也不等于线上验收通过；线上部署验收由用户完成。
